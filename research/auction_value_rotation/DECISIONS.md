| 1 | 2026-07-13 | Session legs reused unchanged from `research/ema21_session_horizon/` (Asia 18:00-02:59, London 03:00-08:29, New York RTH 09:30-15:59 ET) rather than the task's own fallback freeze (London 03:00-09:29 ET) | Per "use existing audited repository session definitions where available" — an audited convention already exists in this repository from a prior generation, and the task's fallback is explicitly conditioned on "if no audited definitions exist" |

Value-area expansion tie-break: add the upper (higher-priced) adjacent bin on a volume tie | Both frozen, deterministic, and arbitrary in the sense the task requires ("use deterministic tie-breaking") — fixed before any profile was built on real data |
| 3 | 2026-07-13 | Each of the 4 profile mappings has its own fixed `expiry_ts` tied to the end of its one target leg instance (mapping 1/2 expire at the end of the leg they feed; mapping 3/4 expire at the end of the overnight/next-RTH leg they feed); the §4E freshness parameter is an *additional*, tighter, within-window gate, never an extension past the mapping's own natural expiry | Matches "do not combine arbitrary profile mappings" and keeps each mapping's active window unambiguous and non-overlapping with adjacent mappings |
| 4 | 2026-07-13 | The 432-cell development grid (per profile-mapping x side) is computed via one master per-excursion, per-acceptance-rule ledger, with the grid applied as post-hoc boolean filters, rather than 432 independent event-detection scans | Statistically identical (verified by a spot-check test re-deriving one grid cell via an independent direct scan), and the only computationally tractable way to genuinely evaluate all 432 combinations rather than a hand-picked subset |
| 5 | 2026-07-13 | Value-area-width band, profile-age band, distance-from-POC band, and realized-volatility band (all matching variables for controls) are tercile cuts computed **on development-year data only**, then frozen and reused unchanged for OOS matching (never recomputed on OOS data) | Prevents any OOS-derived threshold from entering the matching procedure; keeps development and OOS strictly using the same frozen matching rule |
| 6 | 2026-07-13 | "No single development year contributes more than 50% of the pooled effect" (candidate criterion 12) is operationalized as that year's `n_year * \|effect_year\|` share of the sum of `n_year * \|effect_year\|` across the 4 development years, capped below 50% | The task states the requirement without a formula; this is the most direct, symmetric reading ("evidence" weighted by both sample size and effect magnitude) that does not require an arbitrary extra threshold choice |
| 7 | 2026-07-13 | Context variables (§ "Volume and context variables") are implemented in `src/context.py` but the pipeline only invokes that module if >=1 candidate family passes the base-mechanism criteria; if the study is null, no context-variable table is produced | Directly follows "only evaluate context variables for development candidate families that first pass the base mechanism criteria" and "if no family qualifies... do not open OOS outcomes" (by extension, do not run analyses that only exist to further characterize a non-existent qualifying candidate) |
| 8 | 2026-07-13 | Deterministic permutation seed = `20260713`, reused from prior generations' established frozen-seed constant, >=10,000 permutations per family | Fixed before any development-partition result was viewed |
| 9 | 2026-07-13 | 2026 exclusion is enforced by an explicit, tested filter at every pipeline entry point (`src/data.py::filter_partition`), not by relying on the caller to remember to slice; the OOS pipeline additionally refuses to execute at all unless `CANDIDATE_MANIFEST.md` exists in the committed git tree at run time | Two independent, testable guards against both accidental 2026 reads and premature OOS access, per "the OOS pipeline must be technically disabled until a candidate manifest has been committed and pushed" |
| 10 | 2026-07-13 | Reuse only the audited data infrastructure and general no-lookahead/permutation-test/BH mechanics from prior generations (re-implemented locally); no conclusion, level, or classification result imported from any other generation | Consistent with "do not redesign" while keeping this generation self-contained and independently auditable |
| 11 | 2026-07-13 | Five engineering scope decisions for the development grid/classification engine: (a) `MATCHED_INSIDE_STATE` (control 2) samples one representative candidate bar per `(profile, side)` — the last inside-half bar with no edge breach in the trailing 6h — rather than exhaustively enumerating every qualifying inside bar, giving a control population of comparable scale to treatment, matched via the same stratified bands rather than exact 1:1 pairing; (b) the permutation test (10,000 draws) is only run for a grid cell once it already clears the raw count thresholds (>=300 treatment, >=150 usable control) that candidacy requires anyway — smaller cells still get full descriptive/pooled-diff statistics, just no permutation p-value, and are retained in the output tables as `NOT_COMPUTED (underpowered)`; (c) "acceptance family" for BH correction purposes (§8-9) is read as one full `(A,B,C,D,E)` grid cell, corrected within each `profile_mapping` across all `(side x cell)` combinations that have >=1 matched stratum; (d) candidate criteria 8-10 (bin-width support, profile-model-sensitivity support, adjacent-parameter-definition stability) are only evaluated as a second pass for cells that already pass criteria 1-7, 11, 12 under the PRIMARY profile config, not for the full 3,456-cell grid — mirroring the task's own "only compute context variables for families that already pass the base criteria" resource-bounding philosophy; (e) the breach-magnitude band (§7) is dropped from the treatment/control matching-stratum tuple because it has no defined value for `MATCHED_INSIDE_STATE` controls (they never breach) — grid dimension A already imposes a shared breach-depth floor on every treatment row within a given cell, so this does not reintroduce an unmatched comparison | All five are compute/scope-bounding choices forced by the combinatorial size of the 432 x 4 x 2 grid against a finite implementation budget; none of them touch a result, threshold, or definition after seeing development data — they are fixed here, before the grid is run |
| 12 | 2026-07-13 | `stratum_id` (`src/classification.py`) returns a `"-"`-joined string, not a tuple | A tuple-valued numpy object array compared with `==` against a scalar tuple silently mis-broadcasts element-by-element instead of comparing whole tuples, which would corrupt every stratified treatment/control mask; caught by `tests/test_classification.py::test_evaluate_cell_basic_pooled_diff` before any real data was touched |
